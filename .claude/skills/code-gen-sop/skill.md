# code-gen-sop — AI 代码生成标准作业程序

规范 AI 在软件工程场景中的代码生成行为，确保每次代码变更安全、可控、不影响现有功能。

---

## 核心原则

1. **先分析，后动手** — 在写任何代码之前，先理解现有结构和影响范围，输出分析结论让用户确认
2. **最小变更** — 只改动实现需求所必需的代码，不引入无关修改
3. **改后必须校验** — 每次改动都要验证不会破坏其他模块

## 工作流

### Phase 1: 需求分析与影响评估

编码之前必须依次完成：

1. **明确需求边界**
   - 确认要实现的到底是什么功能，验收标准是什么
   - 如有歧义，先向用户确认再动手

2. **理解改动点的调用关系**
   - 对每个要修改的文件，分析它被哪些模块/类引用
   - 如果是修改公共方法签名，必须追踪所有调用方
   - 如果是修改配置类，检查是否有其他模块依赖该配置项
   - 使用 `Grep` 工具搜索引用关系

3. **识别风险**
   - 是否有多个模块共享这段代码？
   - 改动是否会改变既有行为（返回值、异常、入参）？
   - 是否需要向后兼容？

4. **输出影响分析并等待确认**
   ```
   ## 影响分析
   **修改清单：**
   - file A: 修改 reason
   - file B: 新增 reason

   **风险模块：** module X（依赖了 file A 中的方法）
   **兼容性：** 向后兼容/不兼容（需同步修改调用方）
   ```

### Phase 2: 代码实现

#### 范围约束
- 只修改 Phase 1 中确认的文件
- 不改动与任务无关的配置文件（依赖版本、构建配置等）
- 不改动无关模块的代码

#### 代码规范
- **命名**: 遵循项目现有命名风格，不引入新习惯
- **注释**: 不写多余注释。只有当 WHY 不明显时才写一行短注释
- **错误处理**: 只在系统边界（用户输入、外部 API）做校验；内部代码不需要防御性检查
- **异常**: 不吞异常，不捕获无法处理的异常
- **日志**: 和项目已有风格保持一致
- **安全**: 不引入 OWASP Top 10 漏洞

#### 接口兼容性
- 修改现有接口优先向后兼容：新增参数给默认值，不改返回值类型，不改异常声明
- 必须破坏兼容时，提前告知用户并列出所有需要同步修改的调用方

### Phase 3: 变更校验

提交/报告前必须完成：

1. **编译检查**
   - 确认修改涉及的项目编译通过

2. **引用检查**
   - 对修改过的 public 方法、接口、配置项，检查所有调用方是否仍正常工作

3. **回归风险确认**
   - 列出可能受影响的现有功能，确认它们无需修改或已适配

4. **检查清单**
   ```
   □ 只改了计划内的文件
   □ 没有修改无关配置文件
   □ 编译通过
   □ 公共接口/方法向后兼容（或已同步修改所有调用方）
   □ 不影响其他模块
   □ 没有引入安全漏洞
   ```

## 与用户交互方式

- Phase 1 分析结论必须输出让用户确认，确认后再进入编码
- Phase 3 完成后输出校验结果
- 遇到不确定的（如某个调用方是否要改），问用户，不要自行假设
- 每个 Phase 完成时做简短的状态同步

## 安全红线

- 不修改认证、密钥、权限相关配置
- 不引入有已知漏洞的依赖版本
- 不硬编码密钥、密码、Token
- 不跳过 git hooks（--no-verify）
- 不改动数据库密码、API Key 等敏感配置
