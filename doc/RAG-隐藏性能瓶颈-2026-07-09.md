# RAG 服务隐藏性能瓶颈分析

**日期**: 2026-07-09

---

## Q: 还有哪些需要方面影响性能

## A: 补充之前未覆盖的 8 个关键性能维度

---

### 1. 文档接入（Ingestion）性能

当前文档处理是同步阻塞的，且存在隐藏问题。

| 问题 | 影响 | 改进 |
|------|------|------|
| 大文件（100MB+ PDF）解析耗时久 | 阻塞整个导入流程 | 加超时 + 限制文件大小 |
| PDF/Word 解析 CPU 密集 | 与查询请求争抢 CPU | 解析线程池隔离（用 `ingestionExecutor`）|
| 全部读入内存后再处理 | 大文件可能 OOM | 已有每文件立即 flush ✅，但文本内容仍全量在内存 |
| Embedding API 调用无重试 | 偶发失败导致整个文档丢失 | 加 exponential backoff 重试 |

---

### 2. LLM 调用效率 —— Token 浪费

当前 Prompt 将所有参考信息拼接后发给 LLM：

```java
"参考信息：\n%s"  // 最多 8000 字符
```

问题：**上下文越长 → token 越多 → LLM 推理越慢 → 费用越高**。

| 优化 | 效果 |
|------|------|
| 压缩过滤：只传高分的 2-3 条，而不是全部 topK | 减少 token → 更快 + 更便宜 |
| MapReduce：先让 LLM 逐个判断每条是否相关，再拼接 | 精度提升，但延迟增加 |
| 结构化引用：用 `<doc id=1>...</doc>` 格式替代纯文本 | LLM 更容易定位，减少 re-read |

---

### 3. 连接管理 —— 隐藏的瓶颈

当前项目存在的连接问题：

```
DeepSeek API 调用         DashScope Embedding 调用        PostgreSQL
     │                          │                            │
     ▼                          ▼                            ▼
  WebClient(默认)           RestTemplate(默认)           HikariCP(默认 10)
  无超时配置                   无超时配置                   无显式配置
  连接泄漏风险                  连接泄漏风险                  pool 偏小
```

| 连接 | 当前风险 | 必须加的配置 |
|------|---------|-------------|
| DeepSeek HTTP | 无超时 → 请求卡死 | `connectTimeout=5s`, `readTimeout=30s` |
| DashScope HTTP | 同上 | 同上 |
| PostgreSQL | 高峰期连接不够 | `maximum-pool-size: 20~50`, `connection-timeout: 5000` |

---

### 4. HNSW 索引退化 —— 随时间变慢

pgvector 的 HNSW 索引随着不断写入会逐渐退化：

```
时间线：
  第1天：10万向量，查询 5ms
  第30天：新增 2万向量，查询 15ms   ← 索引碎片化
  第60天：新增 5万向量，查询 30ms   ← 索引不够紧凑
```

**解法** — 定时重建索引：
```sql
REINDEX INDEX CONCURRENTLY vector_store_hnsw_idx;
```

---

### 5. 序列化开销

Controller 返回 `QueryResponse` 走全套 Jackson 序列化。每次返回包含：
- answer（数百字）
- references × 5（每条约 200+ 字）

高并发下 JSON 序列化 + 网络传输有可感知开销。优化：加 `brief=true` 参数跳过 references 内容字段。

---

### 6. 冷启动（Cold Start）

| 场景 | 耗时 | 原因 |
|------|------|------|
| 首次部署后第一个请求 | 500ms - 2s 额外延迟 | HNSW 索引从磁盘加载到 shared_buffers |
| JVM 首次响应 | 秒级 | JIT 编译热点方法 |

解法：加**预热接口** `POST /rag/admin/warmup`，上线前发一个假查询预热索引和 JIT。

---

### 7. 日志 I/O 开销

当前配置 `cn.project.base.ragpgvector: DEBUG`，每个查询请求打多条日志：

```
DEBUG Query rewritten: ...
INFO  Query completed in 1234ms retrieved...
WARN  No relevant documents found...
```

高并发下（1000 QPS × 3-5 行/请求 = 每秒 3000-5000 条日志），对磁盘 I/O 是较大压力。生产建议降为 INFO。

---

### 8. 安全与认证开销（未来接入时）

后续如果加 JWT/OAuth 认证，每次请求额外开销：
- Token 解析 + 签名验证（RSA/ECDSA）：约 0.5-2ms
- 权限校验 / Redis 查询

高并发下（1000+ QPS）不可忽略。解法：本地缓存公钥 + 异步刷新。

---

### 完整的性能影响优先级

```
影响程度排序（从大到小）：

★★★★★  LLM API 延迟（远大于其他所有因素之和）
★★★★☆  Token 浪费（过长的上下文 → 更慢 + 更贵）
★★★★☆  连接配置缺失（无超时 → 线程泄漏 → 服务雪崩）
★★★☆☆  文档解析 CPU 开销（大 PDF 上传时劫持所有 CPU）
★★★☆☆  日志 I/O（高并发下的磁盘压力）
★★☆☆☆  HNSW 索引退化（写入多周后显著）
★★☆☆☆  冷启动（部署后前几个请求慢）
★☆☆☆☆  序列化开销（微秒级，除非传超大量数据）
```
