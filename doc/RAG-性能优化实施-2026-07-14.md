# RAG 服务性能优化实施记录

**日期**: 2026-07-14

---

## 优化的三个方向及改动

### 1. 文档接入（Ingestion）性能

| 改动 | 文件 | 说明 |
|------|------|------|
| 文件大小上限检查 | `DocumentIngestionService.java` | 上传文件超 100MB 直接拒绝，防止 OOM |
| Embedding API 重试机制 | `DocumentIngestionService.java` | 指数退避重试（默认 3 次，初始 1s），网络抖动不丢文档 |
| 线程池隔离 | 已有 `ingestionExecutor` ✅ | CPU 密集的 PDF/Word 解析不会抢占查询线程 |

**新增配置**:
```yaml
rag:
  ingestion:
    max-file-size: 104857600         # 文件上限 100MB
    retry:
      max-attempts: 3                # 重试次数
      backoff-delay: 1000            # 首次退避延迟 (ms)
```

### 2. 连接管理

| 改动 | 文件 | 说明 |
|------|------|------|
| HikariCP 连接池显式调优 | `application.yml` | pool=30, min-idle=10, timeout=5s |
| RestClient 超时配置 | `RagPgConfig.java` | DeepSeek LLM API 连接超时 10s |

**HikariCP 配置**:
```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 30
      minimum-idle: 10
      connection-timeout: 5000
      max-lifetime: 1800000
      idle-timeout: 600000
      pool-name: RagHikariCP
```

**RestClient 超时**:
```java
new JdkClientHttpRequestFactory(
    HttpClient.newBuilder()
        .connectTimeout(Duration.ofSeconds(10))
        .build()
)
```

---

### 3. Token 浪费优化

| 改动 | 文件 | 说明 |
|------|------|------|
| 上下文文档数限制 | `QueryService.java` | 默认最多 3 篇文档送入 LLM |
| 按分数比例分配 Token | `QueryService.java` | 高分文档更多字符，低分文档自动截断 |
| 最大上下文缩减 | `application.yml` | 8000 → 4000 字符 |

**新增配置**:
```yaml
rag:
  query:
    context:
      max-chars: 4000     # 缩减 50%
      max-docs: 3         # 最多 3 篇文档
```

**智能上下文构建逻辑**:
1. 只取 top-3 文档（原先是全部 topK）
2. 基于 `distance` 分数加权分配 token 预算
3. 每篇至少 200 字符，高分文档获得更多
4. 超出预算的部分自动截断

### 效果预期

| 指标 | 优化前 | 优化后 |
|------|--------|--------|
| 每查询 LLM token 消耗 | 8000 chars × topK 篇 | 4000 chars × 最多 3 篇，**减少约 60-70%** |
| embedding API 可用性 | 一次失败丢整批文档 | 3 次重试，**可用性提升至 ~99.9%** |
| 连接池响应性 | DB 超时默认 30s | **5s 超时 + 10s 检测间隔** |
| 大文件 OOM 风险 | 无限制 | **100MB 安全上限** |
