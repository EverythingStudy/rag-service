# RAG 服务性能提升全面分析

**日期**: 2026-07-09

---

## Q: 在rag服务中，需要提升性能。1.服务本身的并发支持，可以分布式部署多个rag服务 2,向量数据库如何支持高并发 3.模型调用如何支持高并发 4.实际应用中 向量库需要很大吗，不同的向量数据库 的性能瓶颈如何

## A: 基于项目现有架构（Spring Boot 3.2 + pgvector + DeepSeek/DashScope）逐一分析

---

### 一、服务本身的并发支持与分布式部署

**当前现状**：
- 同步查询走 Tomcat 线程池，默认 200 线程，每个请求占用一个线程等待 LLM 响应（1-10s）
- 流式查询用 WebFlux（非阻塞），不占 Tomcat 线程
- 无状态设计，理论上可以水平扩展

**优化要点**：

| 问题 | 方案 | 具体实现 |
|------|------|----------|
| LLM 调用阻塞 Tomcat 线程 | 同步查询改为异步 + WebFlux | 将所有查询改为 streaming + Flux，彻底释放 Tomcat 线程 |
| 分布式部署 | Nginx/K8s 负载均衡 | 服务无状态，直接水平扩展。流式 SSE 需配置 proxy 关掉 buffer |
| 共享状态 | 外部化 session/cache | `chatId` 已预留但未实现，分布式时需 Redis 存对话历史 |
| 限流 | 分布式限流 | 接入 Redis + Lua 脚本做令牌桶，防止突发流量打爆 API |
| 熔断降级 | Resilience4j | 对 DeepSeek/DashScope API 调用加 CircuitBreaker + 降级兜底 |
| 线程池隔离 | 查询与写入隔离 | 查询链路用 Tomcat 线程（或 WebFlux），写入用独立线程池（已有）|

**代码级改动量**：
- 同步查询改为纯 WebFlux：改写 Controller 返回 `Mono<QueryResponse>`，QueryService 的 LLM 调用改为异步
- 配置项：`server.tomcat.threads.max` 根据部署规格调优，`spring.webflux.base-path` 统一前缀

### 二、向量数据库的高并发支持

**pgvector 的并发特性**：
- 基于 PostgreSQL 的行级锁和 MVCC，读写互相不阻塞
- HNSW 索引：**读操作是纯 CPU + 内存扫描**，不涉及锁争用，并发能力主要受 CPU 核数和 shared_buffers 限制
- 写操作（INSERT/UPDATE）：HNSW 索引维护需要写锁，**高并发写入是瓶颈**

**pgvector 高并发调优参数**：

```ini
# 关键 PG 配置
max_connections = 200                    # 默认 100，需放大
shared_buffers = RAM × 25%               # 向量索引尽量常驻内存
effective_cache_size = RAM × 50%         
work_mem = 64MB                          # 单次排序/哈希可用内存
maintenance_work_mem = 2GB               # autovacuum 和索引维护
jit = off                                # 向量查询关掉 JIT，提升稳定性
```

| 配置/优化 | 说明 |
|-----------|------|
| HikariCP pool size | `maximum-pool-size = (CPU核数 × 2) + 有效磁盘数`，控制在 20-50 |
| HNSW 参数 | `m = 16~32`，`ef_construction = 200~400` |
| 查询时 ef | `ef_search = topK × 1.5` 平衡速度与召回 |
| 读写分离 | 写入走主库，只读查询走副本库的 pgvector（PG 流复制）|
| 批量写 | 已有 `batch.size=50` ✅，写吞吐可控 |

**不同向量数据库并发能力对比**：

| 数据库 | 10K 向量 | 1M 向量 | 10M 向量 | 100M+ | 核心瓶颈 |
|--------|----------|---------|----------|-------|---------|
| **pgvector (HNSW)** | ✅ 极好 | ✅ 好 | ⚠️ 一般 | ❌ 差 | Postgres 连接数 + shared_buffers |
| **pgvector (IVFFlat)** | ✅ | ✅ | ⚠️ 需定期重建 | ❌ | 精度下降，lists 调优困难 |
| **Milvus** | ✅ 过度 | ✅ | ✅ | ✅ | 运维复杂（etcd + 多组件）|
| **Qdrant** | ✅ | ✅ | ✅ | ✅ | RAM 占用 | 
| **Elasticsearch** | ✅ | ✅ | ⚠️ | ⚠️ | 写入 merge 压力大 |
| **Chroma** | ✅ 开发用 | ❌ | ❌ | ❌ | 单进程，不支持集群 |

> 本项目规模下（< 500 万向量），pgvector 完全够用。瓶颈不在 DB，在 LLM 调用。

### 三、模型调用如何支持高并发

这是 RAG 服务**最大的瓶颈**——LLM 调用延迟极高（1-10s），且受限于 API 配额。

**当前现状**：
- `QueryService` 直接调 `chatClient.prompt().call().content()` —— 同步阻塞
- 流式已用 WebFlux + `Flux<String>` ✅，但同步查询没走 WebFlux

**分层优化架构**：

```
请求层
  ↓
Rate Limiter (Redis 令牌桶)     ← 防止打爆 API 配额
  ↓
请求队列 / 优先级调度
  ↓
Semaphore / 并发数控制            ← 控制在 API 并发限制内
  ↓
Circuit Breaker                  ← API 故障时快速降级
  ↓
WebClient (HTTP 连接池)          ← 非阻塞，复用连接
  ↓
DeepSeek API
```

**具体方案**：

| 方案 | 效果 | 实现方式 |
|------|------|----------|
| **全部改为流式** | 同步请求也做成 SSE，TTFT 降低 80% | Controller 统一返回 `Flux<String>`，WebFlux 天然非阻塞 |
| **语义缓存** | 相同/相似问题直接命中缓存，完全跳过 LLM | Redis + 向量缓存（query embedding 相似度 > 0.95 直接返回历史结果）|
| **并发控制** | 控制 DeepSeek API 并发数 | `Semaphore(5)` 限制最多 5 个并发调用 |
| **连接池复用** | 避免每次调用建 TCP 连接 | Spring AI 默认用 `WebClient`，调大 `maxConnections` |
| **备用模型** | API 不可用时降级 | 配置 DashScope Qwen 或本地 Ollama，CircuitBreaker 自动切换 |
| **虚拟线程** | 同步请求不阻塞平台线程 | Java 21 虚拟线程，一行配置启用 |

### 四、向量库容量需求与性能瓶颈

#### 容量估算公式

```
单向量大小 = dimensions × 4 bytes (float32)
HNSW 索引 = 原始向量的 1.5~2×
元数据    = 约 200 bytes/条

总容量 ≈ 向量数 × (dim × 4 × (1 + index_overhead) + metadata)

举例：
  1万向量 = 1万 × (1536×4×2.5 + 200) ≈ 156MB
  10万向量 ≈ 1.5GB
  100万向量 ≈ 15GB     ← 舒适区上限
  1000万向量 ≈ 150GB   ← 需要迁移
```

#### 不同规模下的瓶颈

| 向量量级 | 推荐方案 | 瓶颈 |
|---------|---------|------|
| < 10 万 | pgvector（当前） | 几乎无瓶颈 |
| 10 万 - 100 万 | pgvector + 足够 shared_buffers | 索引加载时间，内存容量 |
| 100 万 - 1000 万 | pgvector（HW 增强）或 Qdrant | HNSW 图遍历速度，disk I/O |
| > 1000 万 | Milvus / Qdrant 集群 | 分布式协调开销，网络延迟 |

---

### 总结：本项目的性能天花板

```
瓶颈排序（从大到小）：
1. LLM API 延迟（1-10s）      ← 语义缓存 + 流式可大幅缓解
2. 同步阻塞的查询路径          ← 虚拟线程 + WebFlux 可解决
3. 无分布式限流/熔断            ← Resilience4j + Redis 可解决
4. Pgvector 索引在千万级以上    ← 本项目远未触及
5. 无查询结果缓存               ← 语义缓存可大幅提升重复查询
```

**最立竿见影的 3 件事**：
1. 开启 Java 21 虚拟线程（配置一行 `spring.threads.virtual.enabled: true`）
2. 同步查询也改为流式返回（类似已有的 `/rag/query/stream`）
3. 加语义缓存（query embedding + Redis，重复问题毫秒级响应）
